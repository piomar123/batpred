# Fork maintenance (piomar123/batpred)

<!-- cspell:ignore piomar rerere worktrees ziglang -->

This fork carries changes that aren't in upstream Predbat yet. They're kept as one branch each and combined into a generated branch, `patched`, which is what gets deployed.

## What's in it

| Change | Upstream | apps.yaml key (absent = upstream behaviour) |
| --- | --- | --- |
| Net settlement of import/export within wall-clock windows, for tariffs that net them per hour or quarter-hour before billing (e.g. Polish net-billing) | [#5429](https://github.com/springfall2008/batpred/pull/5429) | `metric_net_settlement_window_minutes` |
| Export energy budget: only export battery energy that came from PV | [#5538](https://github.com/springfall2008/batpred/pull/5538) | `export_budget_mode` |
| A failed auto power curve search is retried about hourly instead of on every poll (12-15 s of CPU a minute on a Pi 4) | not offered yet | - |
| Charge/discharge power deadband 2% instead of 5%, so low-power targets on a ~3.5 kW battery are written | fork-only | - |

The kernel binaries (`apps/predbat/prediction_kernel_lib_*.so`, all six platforms) are rebuilt for this combination with local ABI/parity numbers, so an upstream binary is never loaded against it.

## Installing a release

Releases are the `v<upstream>-piomar.<n>` tags (see [Releases](https://github.com/piomar123/batpred/releases)); use a tag, not the moving `patched` branch. Copy the top-level files of `apps/predbat/` from the tag over the ones in the directory your Predbat runs from (where `predbat.py` is), keeping your `apps.yaml`, and restart Predbat. Turn `auto_update` off (and don't pick a version in Predbat's update selector), or Predbat replaces it with upstream's next release. The log should show `Prediction kernel loaded from ...`; a stale binary only logs a `Warn:` and falls back to Python.

## Branches

| Branch | What it is | How it changes |
|---|---|---|
| `main` | exact copy of upstream `main` | fast-forward only (`gh repo sync piomar123/batpred -b main`) |
| one branch per change, listed in `branches.txt` | the only copy of each change; most are the head of an upstream PR | rebased onto upstream `main` for upstream review |
| `fork-glue` (this branch) | `tools/fork/`: the branch list and the rebuild script | rarely |
| `patched` (the fork's default branch) | generated by `rebuild.sh`, never edited by hand | rebuilt and force-pushed |
| `v<upstream>-piomar.<n>` tags | releases, what the Pi runs | never moved |

## Rebuild

```bash
tools/fork/rebuild.sh                                # build on upstream main and test
tools/fork/rebuild.sh --push --tag v9.4.1-piomar.2   # and publish it
```

The kernel needs zig 0.16.0, the version upstream's CI pins, on the machine that runs the script (not on the Pi). Put the official tarball from ziglang.org, checked against its published SHA-256, in `~/.local/opt/zig-0.16.0/`, or point `ZIG=` at another copy. Homebrew's `zig` follows the latest release, so it's only used as a fallback, with a warning when it isn't 0.16.0.

The script resets `patched` (in the worktree `.worktrees/patched`) to the base, then merges each branch from `branches.txt` with `--no-ff`, then `fork-glue`. Then it gives the kernel local ABI/parity numbers (1000 + upstream's) and rebuilds the six kernel binaries with zig. Last, it runs the full unit test suite and the kernel parity check. `git log --first-parent patched` shows one merge per branch.

- **Conflicts** between branches are replayed by `git rerere` (enabled by the script; the resolutions live in this clone's `.git/rr-cache`). A new conflict stops the script: resolve it in `.worktrees/patched`, `git commit`, and run the script again.
- **Kernel binaries** are never merged; either side is taken and all six are rebuilt.
- **Base:** upstream `main` by default. `--base v9.4.0` works only when every branch is based at or before that tag; the script refuses otherwise, because merging a newer branch would also bring in the upstream commits between the tag and the branch's base.
- **Tests** need `coverage/venv` in `.worktrees/patched` (a symlink to an existing venv is fine).

## When things change

- **A branch changes** (review fixes, a rebase): push the branch, rebuild.
- **Upstream merges a PR:** delete its line from `branches.txt` on `fork-glue`, push, rebuild. Nothing has to be reverted, however upstream merged it.
- **A new change:** branch it off upstream `main`, push it, add a line to `branches.txt`, rebuild.
- **A release:** rebuild with `--push --tag`. A tag name ends in `-piomar.<n>`, after `git describe` of the base.

## Known combination

Net settlement (springfall2008/batpred#5429) and the export budget (springfall2008/batpred#5538) both add fields to the end of `PkContext` and both claim ABI 8 / parity 18 upstream. Here, net settlement's fields come first and the export budget's after them, in both `prediction_kernel.cpp` and `prediction_kernel.py`; everywhere else both sides are kept. If the rerere cache is lost, resolve the merge that way again.
